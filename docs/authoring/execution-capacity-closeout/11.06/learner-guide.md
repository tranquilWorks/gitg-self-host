# 11.06 — Project and workflow management

## Deliver something that can be inspected

A workflow makes the state of a shared result visible: what is in scope, who has agreed to own work, what input is missing, what risk matters and what counts as done. A board is useful only when its cards lead to inspectable outputs. Drafting a sheet is different from testing and delivering it.

Here you will carry a small paper instruction sheet through scope, inspection, drafting, testing, rework and closeout. Allow 30 minutes of work and three two-minute checkpoints within it. You can finish the supplied simulation now with paper or a text editor. No cupboard visit, account, purchase, private information or real participant is needed. You will genuinely produce a sheet and self-review record; the depicted cupboard and messages are fictional. Team delivery and actual reader use remain separate evidence.

Use this route for ordinary coordination within your authority. It does not confer managerial authority over unwilling people or permit changes to a shared space. A solo worker can own several cards, but cannot supply another person's consent by writing their name on a board.

## Reference: card states are claims

**Scope** fixes the result and exclusions. **Ownership** identifies a consenting person responsible for the next output; it does not mean that person must do every step unaided. **Dependency** identifies an input that must exist before work can proceed. A **risk** is an uncertain event with an impact, trigger, owner and response. A **decision** preserves a choice, date, reason and consequence. **Status** follows evidence, not confidence or elapsed time.

Use Ready, Doing, Blocked and Done. A Ready card has the required inputs. Doing means work has actually begun. Blocked records the missing input, who will seek it and the next checkpoint. Done requires the card's output and acceptance condition. If a later test exposes a defect, preserve the prior result and reopen the affected work with a dated reason. Deferred or cancelled is a visible disposition, not a disguised Done.

Limit Doing to one card for this sole worker. Work waiting for someone else's input moves to Blocked; it does not keep consuming a fictional second worker. The board may show several blocked items, but each needs a next decision. Do not repeatedly send reminders or assign unwilling helpers to clear it.

## A different worked example

A one-person project makes a three-song event list. The owner agreed to names and order, not to purchase music. Scope is Done when that agreement is recorded. Draft is Done when all three names and their order exist. Review is Blocked until the consenting host's reply arrives. “Asked host” is an output of a contact task, not review acceptance. If the event is cancelled, archive the reason and release the optional playlist goal; do not label the event delivered because every draft card is finished.

## Complete project packet: a fictional hobby cupboard

The depicted keeper, Mira, has supplied this simulated brief: “Write an instruction sheet for finding and returning the hole punch and blue tape. You may describe the cupboard. Do not move objects or relabel it. Use locations and object names only, with no personal information. Finish a self-reviewed paper version today. A shared release would require my separate approval; I have not granted that.” This is a fictional permission record for the case, not permission to alter any real space.

You choose to own all five cards in the paper route. Record that choice. Mira is the case's input contact, not a real person you must contact. The optional live route requires actual willing owners and a suitable space.

### Inspection materials

Face the cupboard. “Left” and “right” are from the reader's position facing it. The cupboard has two labeled shelves, Upper and Lower, each with Left and Right trays. The labels are large text. Items occupy these exact positions:

| Location | Visible label | Contents |
| --- | --- | --- |
| Upper Left | PUNCH | hole punch |
| Upper Right | STRING | string spool |
| Lower Left | BLUE TAPE | blue tape roll |
| Lower Right | BLANK CARDS | blank cards |

No drawers, locks or hidden items exist. Items return to the same tray. All are harmless paper-craft materials; actual physical handling is unnecessary for the paper route.

The inherited Version 0 sheet reads: “Face the cupboard. The hole punch is Upper Left; return it to Upper Left. Blue tape is Lower Right; return it to Lower Left.” Keep this artifact unchanged in the record so the error can be traced. Do not call Version 0 accepted.

### Definition of done

For the **paper deliverable**, a complete Version 1 sheet must correctly direct a reader to find and return both target items, define viewpoint, use the visible labels, exclude personal information, and have a saved four-step self-review plus responsible closeout. Label the evidence self-review of a fictional layout. A **shared release** additionally needs the keeper's real approval and an actual willing reader's retrieval/return attempt. The source exercise cannot satisfy those two live conditions.

### Five starting cards

| Card | Output and acceptance | Dependency | Initial state |
| --- | --- | --- | --- |
| S scope | Brief, authority, exclusions and paper done rule recorded | Supplied brief and your ownership choice | Ready |
| I inspect | Four-location inventory copied exactly | S | Blocked |
| D draft | Version 1 sheet with viewpoint, labels and both return instructions | I | Blocked |
| T test | Four retrieval/return checks with actual paper results, route labeled | D | Blocked |
| R revise and close | Defect disposition, retest, delivery record and open-live-work list | T | Blocked |

For every card add `owner | due window | missing input | unblock owner | next check | artifact reference`. Today's paper window is the next 30 minutes; this is a suggested learning allowance, not a speed test. If you need longer, record it without claiming a missed external promise. Each blocked card's immediate missing input is the predecessor output; you own producing it. In a live project, distinguish that worker from the person responsible for asking for an unavailable external input.

### Action 1 — Establish scope and produce the first output

Write the S scope card from the brief, choose ownership and define the work-in-progress limit of one. Move S to Doing, create its scope artifact, then to Done. At **checkpoint 1**, identify which card is now Ready and explain why the others remain Blocked. Copy the inspection table as I's output and record its comparison to the packet. Only then move I to Done.

Record two risks: an ambiguous location could cause the sheet to fail; an absent keeper approval could block a later shared release. For each, give the trigger and action. Your paper route can resolve the location risk but must leave real approval unestablished. Do not assign a due date to a person who has not agreed to respond.

### Action 2 — Draft, test and keep the decisions

Produce Version 1 using the table. Keep Version 0 separate. At **checkpoint 2**, inspect that the sheet actually exists before closing D. Write a decision record: `time/order | changed wording | reason tied to inventory | affected acceptance check`. You may use step order instead of invented timestamps in this simulation.

Run T yourself, line by line: locate punch, return punch, locate tape, return tape. Record the location your written instruction actually names, compare it with the table and mark pass/fail. This is an actual inspection of your written artifact, not an independent user test. Save failures before repairing. Open [later-packet.md](later-packet.md) only after saving this first test; it supplies an additional simulated reader report on Version 0 and a future-release branch.

### Action 3 — Rework and close the right deliverable

If your sheet fails, reopen D, explain the defect, correct a new version and retest all affected instructions. A test passing on one version does not prove a changed version. At **checkpoint 3**, verify the paper definition of done against the saved sheet and test, then write: `delivered artifact/version | verification route/results | resources returned or none borrowed | unresolved obligations | next owner/action | closure status`.

No physical resources are borrowed in the default, so record “none borrowed,” not a fictional return. Save the final sheet with the closeout record; that is delivery of your paper learning artifact to your own workspace. Keep shared release pending; no actual keeper or learner receipt is supplied. If scope is cancelled, preserve the reason and state which work is abandoned.

Attempt [check-prompts.md](check-prompts.md) before [check-answers.md](check-answers.md). The corrective guidance supplies a complete acceptable sheet and discriminates draft, verified paper output and released project.

## Access, challenge and transfer

Use large-text cards, an audio board or dictation. A reader may transcribe the source table; the learner still makes the state and acceptance decisions. A supported self-review remains supported self-review. This tabletop route exercises coordination reasoning and document production, not physical access or team leadership.

For a harder supplied variation, the keeper permits a future move of tape to Upper Right only after the string is removed, but there is no report that either happened. Keep the current sheet unchanged; add a blocked change card, missing confirmed layout, input contact Mira, and a checkpoint before any revised shared release. A proposed layout is not a current inventory.

Later, use one small real project with consenting collaborators. Keep the actual scope, outputs, replies, rework and closure. Review whether blocked inputs became visible early enough to act. Do not infer fewer surprises from a board alone.

**Supportive:** The paper sheet and four checks exist, defects are repaired, and release remains pending where actual approval is absent.

**Mixed:** A good draft exists but its return instructions were never tested.

**Contradictory:** A blocked approval becomes Done through silence, a failed instruction is hidden, or an unwilling person is assigned ownership.

**Inconclusive:** The columns are configured but no inspectable output is produced.
