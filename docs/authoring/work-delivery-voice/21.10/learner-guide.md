# 21.10 — Innovation and improvement

Test a modest file-labeling change against a defined user problem. Allow twenty minutes to prepare, four short paper trials and fifteen minutes to compare. The materials below replace real files. Do not rename shared documents, delete history or experiment on other people's data. A change can teach something useful even when you decide not to adopt it.

## Improvement requires a comparison and a cost

Innovation starts with an assumption worth questioning, not a need to use a novel tool. If people cannot identify the current approved document, a plausible hidden assumption is that everyone remembers the history. The desired value is correct selection with less checking, not more sophisticated filenames. State that outcome before seeing results so an attractive new system cannot redefine success around what it happens to do well.

Combine ideas for a reason. A readable version label can distinguish drafts, while an explicit current marker can communicate a decision. These ideas address different uncertainties. A timestamp does not itself establish approval, and a marker can become stale. The combined proposal therefore needs both a source of authority and an owner who keeps the marker consistent. A second artifact may reduce one person's search while creating another person's maintenance work.

Use a baseline that reflects the problem fairly. Do not choose impossible old cases and easy new ones. Give each condition the same number of candidates, a known approved answer, similar distractors and the same selection question. Record correctness and extra checking separately. A fast wrong choice is not a successful efficiency gain. Opening fewer files also does not establish elapsed-time savings if no time was measured.

Small comparisons have limits. A person may learn the task after the first trial, or the changed sets may be easier despite your effort to match them. A bundled change cannot tell you whether labels or the marker caused any difference. Two uses per condition support a bounded design observation, not a stable error rate or a general causal claim. Preserve any failure of the new method instead of dropping it as an unfair exception.

Count setup, upkeep and shifted burden. Work spent applying labels and reconciling a marker is part of the proposed process. Costs may still be worthwhile, but adoption needs the affected owner's agreement and a credible maintenance arrangement. A revised design is another hypothesis until tested. “We will fix the marker” is not evidence that the fixed process works.

Keep, revise and reject are all legitimate outcomes. Rejecting a more complicated system can be a good result if it reveals that the current method already works or that a simpler shared record would suffice. Preserve useful learning about the original assumption. Creativity is not personal worth, so it need not be defended by exaggerated claims or forced adoption.

## Worked example

A team adds “CURRENT” to one filename. A later approved revision arrives, but the old marker remains. The next user selects the old document quickly. The change reduced checking while undermining correctness. A better question is who maintains authoritative status and how a change reaches that record. Renaming the same failure “user error” would conceal a design dependency.

## Four complete paper file sets

The task is to select the **currently approved notice**, opening as few simulated content cards as needed. Each set has five candidates. Filename is visible; opening a card reveals its status. The recorded correct answer comes from the fictional owner's approval ledger. A later draft is not automatically approved. Use the sets in order A, B, C, D and record that order as a limitation.

| Set | Visible names in order | Status inside, in matching order | Ledger answer |
| --- | --- | --- | --- |
| A, current method | notice; notice-final; notice-new; notice-copy; notice-notes | v1 superseded; v2 approved current; v3 unapproved draft; v1 copy; notes only | notice-final, v2 |
| B, current method | plan; plan-edited; plan-final; plan-copy; plan-notes | v1 superseded; v3 unapproved draft; v2 approved current; v1 copy; notes only | plan-final, v2 |
| C, proposed method | C-v1-old; C-v2-CURRENT; C-v3-draft; C-v1-copy; C-notes | v1 superseded; v2 approved current; v3 unapproved draft; v1 copy; notes only | C-v2-CURRENT, v2 |
| D, proposed method | D-v1-old; D-v2-CURRENT; D-v3-draft; D-v1-copy; D-notes | v1 superseded; v2 superseded; v3 approved current; v1 copy; notes only | D-v3-draft, v3 |

Set D intentionally contains a stale visible label and marker. The ledger and card contents are authoritative; this is a supplied maintenance defect, not a puzzle requiring secret information. These labels are synthetic, not instructions to adopt this naming scheme. Comparable candidate structure does not make the trial randomized or blind.

## Decide from the evidence

1. Write the memory assumption, desired benefit, predicted mechanism and one downside. Define success as correct selection, with content openings reported separately. Output: a predeclared comparison question.
2. Save your prediction before the [later packet](later-packet.md). Inspect all four supplied sets using their ledger answers to judge results. Output: four condition-labeled results retaining the new-method failure.
3. Compare correctness, checking and the supplied setup/upkeep burden. State what was not measured and what order or design differences could explain. Output: a bounded comparison, not a causal estimate.
4. Ask what an owner would need to accept adoption. Choose keep, revise or reject and specify the next discriminating test. Output: a conditional decision and an owned maintenance question.

## Support and transfer

Use large-print cards or spoken candidate/status pairs; accessibility does not require hiding the authoritative answer from a supported learner. A harder case contains two current markers: stop and reconcile authority rather than choose the newest timestamp. For actual transfer, obtain permission and use a reversible copy of harmless materials. Respect real change control and keep access, privacy and history intact.
